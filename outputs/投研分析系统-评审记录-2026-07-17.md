## 2. 背景与目标

系统的目标不是自动交易，也不是输出未经约束的选股信号，而是：

```text
先发现值得研究的行业
  → 确认行业处境、周期和产品需求
  → 建立该行业的代表公司池
  → 用轻量数据筛选生存能力、利润弹性和估值
  → 对少量候选做产品、竞争、公告和市场结构深研
  → 用户确认后锁定模拟决策、持有论文和跟踪条件
```

原有指定对象入口必须继续保留：

- 输入公司研究；
- 输入行业研究；
- 输入国内商品期货品种或具体合约研究。

主动机会发现是新增入口，不能破坏上述三类入口，也不能把模拟建议变成自动下单。

## 3. 评审发现

### P0：机会发现默认扫描范围与目标不一致

原设计使用“证券与行业全集 → 本地扫描 → 公司候选”的表述，并写入每周行业与公司全量扫描。这会把机会发现变成全市场个股数据工程，带来不必要的行情、财务、估值、公告全文、存储、内存和 Token 消耗，也不符合用户明确的“先行业、后公司”研究顺序。

结论：必须改为行业优先，行业雷达先运行；公司数据只有在行业入选后分层加载。

### P0：已有组件不能承担全市场 A 股批量扫描

已核对：

- `vendor/ai-berkshire/tools/stock_screener.py` 的默认 `a_share` watchlist 为空，主要是美股和少量港股 watchlist；
- `vendor/ai-berkshire/tools/ashare_data.py` 提供单只 A 股的行情、财务、估值和代码搜索，接口形态不是全市场批量扫描器；
- `luopan` 的公司池是研究边界下的代表公司/候选公司集合，不是完整证券主数据，也不应被强行解释为全市场覆盖；
- `ai-berkshire` 的行业研究能力可以复用，但其中“全球公司扫描”类表述必须被本系统的行业优先资源策略覆盖。

结论：系统不应围绕一个现有组件不存在的“全市场 A 股扫描器”继续设计；只需增加行业雷达、公司池路由和字段映射等薄连接能力。

### P1：数据对象边界没有完全落到设计模型

如果不区分以下四层，调度器很容易把所有数据都当成同一种输入：

| 数据层 | 默认范围 | 作用 |
|---|---|---|
| 证券主数据 | 全市场轻量元数据 | 代码、名称、市场、上市状态、行业归属和行业成员历史 |
| 行业雷达数据 | 行业全集 | 需求、库存、价格、成本、利润、资本开支、供给退出、政策和行业指数/ETF |
| 公司筛选数据 | 入选行业的 10-30 家 | 主营、产品、财务摘要、现金流、负债、成本、份额和估值 |
| 公司深研数据 | 3-5 家，最终 1-3 家 | 原始公告、完整行情、产品/竞争资料、市场结构和深度财务 |

结论：需求文档新增行业优先和分层加载约束；设计文档新增 `industry_radar_snapshots`、`industry_membership_history` 和资源预算字段。

### P1：首期扫描器过多，实施风险偏高

四类机会标签可以保留为产品输出，但首期不应同时建设四个复杂扫描器。建议首期先实现：

1. 周期反转扫描器：需求、库存、价格、成本、利润、资本开支和供给退出；
2. 质量修复扫描器：现金流、负债、治理、产品竞争力、市场份额和估值。

需求加速和瓶颈涨价先通过行业雷达配置与人工/规则触发进入行业候选，待数据质量和验证样本稳定后再独立工程化。

### P1：`luopan`/`ai-berkshire` 的复用边界必须明确

两者应被视为研究资产、研究路由和部分工具的来源，不是本系统的统一证券数据服务。复用规则为：

- 直接复用已有且未过期的行业/公司画像、公司池、八指标、公告索引和研究中间结果；
- 仅对缺失、过期、冲突或无法匹配的字段补采；
- 观点、目标价和买卖表达保存为 `REFERENCE_ONLY`，不能直接成为事实或最终结论；
- `luopan` 公司池保留研究范围、时间截面和完整性声明，不能覆盖 `companies` 主表。

### P1：容量只能作为资源上限

“每轮不超过多少公司”是 Token、内存、存储和研究精力的保护阀，不是必须填满的候选配额。没有合格行业或公司时，空集是合法结果；淘汰对象、证据和重新进入条件必须留痕。

### P2：微信公众号发布继续后置

公众号自动生成/人工发布可以保留架构边界，但必须等研究底座、锁定决策、持续跟踪和质量归因稳定后再实现。当前只保留单向公开草稿转换，不计入首期维护成本和验收主线。

## 4. 最终决策

采用以下正式流程：

```text
行业全集/行业分类
  → 行业雷达
  → 选出少量行业
  → luopan 行业研究与代表公司池
  → 每个入选行业加载 10-30 家公司轻量数据
  → 本地筛选 5-10 家
  → 补充数据 3-5 家
  → AI 深研 1-3 家
  → 用户确认模拟决策与持有论文
```

全市场只维护轻量证券主数据和行业成员历史，不默认维护全市场个股日线、完整财务、估值、技术指标和公告全文。用户明确授权的专项批量任务可以例外执行，但必须记录范围、数量、原因、数据版本和资源消耗。

首期机会发现优先实现“周期反转”和“质量修复”两类确定性扫描能力；需求加速、瓶颈涨价作为行业雷达标签和后续扩展。

## 5. 本次修改清单

### 需求文档

- 将机会发现入口、目标和场景改为行业优先；
- 将发现漏斗改为“行业全集 → 行业雷达 → 行业公司池 → 公司分层加载 → 少量深研”；
- 增加行业雷达最低字段、行业成员历史和公司池分层加载规范；
- 将全量扫描频率改为行业雷达周期更新、行业/候选增量和事件触发；
- 增加默认禁止全市场个股深度数据批量下载的资源约束；
- 在验收标准中加入行业快照、公司池层级和资源边界验证；
- 增加极简、稳定个人、深度投研三档月维护成本估算。

### 设计文档

- 架构图加入行业雷达、入选行业与公司池、分层公司数据加载；
- Phase O 改为 O0-O13 的行业优先工作流；
- 调度器改为 `industry_radar_refresh`、`daily_delta_scan`、`event_triggered_scan` 和 `company_pool_refresh`；
- 新增行业雷达模块和行业优先资源路由；
- 新增 `industry_radar_snapshots`、`industry_membership_history` 及扫描资源预算字段；
- 文件结构增加行业雷达和行业成员数据目录；
- 更新质量控制、实施路线、已有组件关系和运维成本假设。

## 6. 未解决风险与处理办法

| 风险 | 影响 | 处理办法 |
|---|---|---|
| 行业分类口径不一致 | 公司可能被错误纳入或排除 | 保存分类来源、生效时间和人工覆盖，允许多行业映射 |
| 行业级数据覆盖不足 | 雷达漏报或状态滞后 | 标记证据完整度，允许人工补充，保留行业空集和待复核状态 |
| 低频行业数据发布 | 不能提供虚假的日更结论 | 按指标频率更新，报告显示数据截止日和新鲜度 |
| `luopan` 代表公司池不完整 | 漏掉重要公司 | 与行业成员历史、协会资料、`ai-berkshire` 和人工关键公司清单交叉，不声称全覆盖 |
| 免费数据源限流或接口变化 | 任务失败、维护成本上升 | 适配器健康检查、缓存、重试和来源降级；关键字段冲突时暂停结论 |
| 行业改善但公司未受益 | 错误把行业 Beta 当公司机会 | 必须通过产品、客户、份额、收入、利润和现金流传导验证 |
| Token 或内存不足 | 深研中断 | 行业优先、分层加载、`LOCAL_ONLY`、最大深研数和增量复核 |

## 7. 维护成本结论

在已有 Mac 和本地环境，主要使用免费数据源，不部署公网服务且低频调用模型的前提下：

```text
最低新增现金支出：约 0-100 元/月
稳定个人使用：约 100-500 元/月
深度投研运行：约 500-2000 元/月
```

“0-100 元/月”表示不新增商业订阅时的现金支出区间，不表示没有电费、硬件折旧、数据接口不稳定造成的维护工作或个人时间成本。若采购 Wind、Choice、聚宽高级数据、商业行情或行业数据库，成本可能达到数千至数万元/月，应另行评审。

## 8. 评审结论

原设计的问题不是“是否需要机会发现”，而是机会发现的入口层级和数据加载策略错误。修改后，系统保持完整投研平台定位，同时把最昂贵的数据和 Token 使用限制在少量入选行业与候选公司上，满足“先找行业，再找公司”的研究目标。两份文档已按该结论同步修订，后续实现以本评审记录和 v0.7 文档为准。
